# 3x3 rooms sample

A room library of five room kinds, and levels of them on a 3x3 grid, each
built twice: once by compiling the library's rooms with `ssmap room` and
stitching them with `ssmap link`, and once as one ordinary VMF of the same
level (`ssmap link --flatten`) compiled with `ssmap vbsp`. The test suite
checks that the linked map and the whole-map compile agree on everything a
game can observe, for the sample level, its turns, and seeded levels.

Everything in this folder except this README is generated by
`SourceSharp.MapGen.Rooms` and checked by a test to be exactly what the
generator writes. Do not edit the files by hand; change the generator and
regenerate.

## What is here

| Path | What |
| --- | --- |
| `gameinfo.txt` | A game that mounts only this folder, so the sample compiles with no Steam install. |
| `materials/rooms3x3/*.vmt` | The kit's materials. No textures ship; a missing base texture is only a warning. |
| `rooms.vmf` | The room library: the five rooms in a line along +x, 128 units apart, each marked by an `info_room`. |
| `levels/rooms3x3.yaml` | The sample level. |
| `levels/rooms3x3_turn{1,2,3}.yaml` | The same level turned a quarter, a half and three quarters: every room in another cell, turned. |
| `levels/seed_{1,2,9,10}.yaml` | Seeded levels, exactly as `ssmap layout` writes them; 9 and 10 leave two cells empty. |

### The library

One VMF holds every room. Each room is a 256-unit cell built anywhere in
the map, with an `info_room` point entity at the cell's low corner (least
x, y and z) that names it and states the grid and the door kit:

| Key | Here | Meaning |
| --- | --- | --- |
| `name` | `cross`, `tee`, ... | The room's name: its entry in the room pack and what a level calls it. |
| `cell_size` | `256` | The cell's edge; the cell is a cube. |
| `door_width` | `96` | The door opening's width. |
| `door_height` | `224` | The door opening's height. |
| `wall_depth` | `16` | The shell's thickness, and how deep a door plug reaches in from the cell face. |
| `socket_east` ... `socket_south` | (not used) | Optional names for the sockets; the default is the wall's name. |

Everything inside a cell belongs to that room. Point entities between the
cells are ignored; a brush between them, or across a cell's edge, is an
error. The door must let a standing player (32 x 32 x 72) through, standing
on the floor, so a door is the full interior height: `cell_size - 2 x
wall_depth`.

### The kit

Every room is a 256-unit cell with a 16-unit shell. A door socket is a
96-wide opening the full height of the interior, centred on a cell face,
filled by a plug brush of `rooms3x3/doorplug` (`%compileTrigger`, still
solid, so the room compiles sealed). A world brush that exactly fills the
kit's plug box on a wall is that wall's socket. `ssmap link` removes the
plug at a joined socket and keeps it at a capped one.

| Kind | Sockets (room-local) | Feature |
| --- | --- | --- |
| `cross` | east, west, north, south | a structural pillar in the north-west corner |
| `tee` | east, west, north | a player-clip block (`rooms3x3/playerclip`) |
| `corner` | east, north | a grate post (`rooms3x3/grate`, `%compilePassBullets`) |
| `hall` | east, west | a `func_detail` crate |
| `end` | east | a step, and an `info_player_start` |

Every room has a light at its centre. The features stand off the centre and
out of the doorways, so a room turned a quarter is a different map even when
its sockets look the same.

### The level files

A level is a YAML file: the library, the grid's size, and the grid, written
the way the level looks from above with north up.

```yaml
library: ../rooms.vmf        # relative to this file
rows: 3                      # south to north
columns: 3                   # west to east
grid:                        # first line = the NORTH row
  - [end@270,   hall@90, corner@270]
  - [tee@270,   cross,   tee@90]
  - [corner@90, corner,  corner@90]
```

A cell is a room's name, optionally `@` and its rotation in degrees
counter-clockwise seen from above (0, 90, 180 or 270), or `~` for no room.
(`-` would read better, but YAML takes a `-` inside brackets for a
sequence entry, so `~`, YAML's own "nothing", it is.)

Joints are never written. Two sockets that face each other across a shared
wall are joined; every other socket, facing an empty cell, the grid's edge
or a neighbour's plain wall, is capped. A level is only valid if a player
can walk from every room to every other; `ssmap link` refuses a level with
a room nobody can reach, and names it.

The sample level, with world faces in brackets:

```
y=2   end    @270 (S)          hall  @90 (N capped, S)   corner @270 (S, E capped)
y=1   tee    @270 (S, N, E)    cross      (all four)     tee    @90  (N, S, W)
y=0   corner @90  (N, W capped) corner    (E, N)         corner @90  (N, W)
```

## Build and link it

From this folder, with `ssmap` built (`dotnet build src/SourceSharp.MapTools.slnx -c Release`
at the repository root puts it in `bin/Release/ssmap.dll`):

```sh
# list the library's rooms, their cells and their doors
ssmap rooms rooms.vmf

# compile every room of the library into rooms.roompack (the game is this folder)
ssmap room rooms.vmf -game .

# link a level from the packed rooms, without recompiling them
ssmap link levels/rooms3x3.yaml -rooms rooms.roompack -out out/rooms3x3.bsp

# the reference: the same level as one VMF, compiled whole
ssmap link levels/rooms3x3.yaml --flatten -out maps/rooms3x3.vmf
ssmap vbsp maps/rooms3x3.vmf

# both pass the loader's checks
ssmap check out/rooms3x3.bsp maps/rooms3x3.bsp

# a new level of the library's rooms, from a seed
ssmap layout rooms.vmf -rows 4 -columns 5 -seed 7 -empty 0.2 -out levels/mine.yaml
```

Swap in any other level file; the rooms do not need recompiling. Without
`-out`, `ssmap room` writes `rooms.roompack` beside the library, and
without `-rooms`, `ssmap link` looks for it there, writing the map (or the
flattened VMF) beside the level file. `ssmap room` compiles up to
`-threads` rooms at once and writes the same pack at any thread count. The
outputs (`rooms.roompack`, `out/`, `maps/`, and maps beside the level
files) are ignored by git.

## Regenerate it

```sh
dotnet run --project tools/RoomsSample -c Release -- --out samples/rooms-3x3    # rewrite the files
dotnet run --project tools/RoomsSample -c Release -- --check samples/rooms-3x3  # say what differs
dotnet run --project tools/RoomsSample -c Release -- --list                     # the levels the tests check
```

### A large library for stress runs

`--stress` writes a game folder like this one whose library holds many
distinct rooms on the same kit (1024 by default, up to 2160): the five kinds,
each varied by where its feature stands, its size, extra corner blocks and
lights (`RoomsStressLibrary`). The library is about 22 MB for 1024 rooms, so
it is written to a scratch folder and never checked in:

```sh
dotnet run --project tools/RoomsSample -c Release -- --stress /tmp/rooms-stress        # 1024 rooms
dotnet run --project tools/RoomsSample -c Release -- --stress /tmp/rooms-stress 200    # a smaller one
cd /tmp/rooms-stress
ssmap room rooms.vmf -game . -threads 4
ssmap layout rooms.vmf -rows 16 -columns 16 -seed 1 -out levels/l16.yaml
ssmap link levels/l16.yaml -out out/l16.bsp
```

`Rooms3x3SampleTests.TheCheckedInSampleIsWhatTheGeneratorWrites` fails when
this folder and the generator disagree, and
`Rooms3x3CommandsTests.TheSampleSeededLevelsAreWhatSsmapLayoutWrites` when
the seeded files are not what `ssmap layout` writes for their seeds.

## What the tests check

### The levels

The default test run checks **16** levels (`Rooms3x3Permutations.DefaultCases`):

1. the sample level and its three whole-level turns (4);
2. twelve levels the seeded generator (`ssmap layout`, `LevelGenerator`)
   draws from the library with the fixed seeds 1 to 12, the last four with
   a quarter of the cells (two) left empty.

The generator places any of the library's rooms, as often as it likes: it
picks a random spanning tree of the occupied cells, whose walls must be
doorways, and fills the cells by a seeded backtracking search in which a
wall shared by two rooms has a socket on both sides or on neither. Every
room is therefore reachable, by construction; a fact checks it over many
seeds and grid shapes, with and without empty cells.

The exhaustive sweep instead permutes the sample level's own nine rooms
(one cross, two tees, four corners, one hall, one end) over every cell and
rotation. It is valid when every shared wall has a socket on both sides or
on neither, and the joints connect all nine rooms. There are **85,088**
valid arrangements (`Rooms3x3Permutations.All`, a backtracking search in a
fixed order).

### The criteria

The linked BSP and the flattened level's BSP are not byte-equal and are not
meant to be: a whole-map compile builds one tree over all the rooms, and the
link hangs one room tree per room under a grid of cell planes. They are
compared in what a game observes (`Rooms3x3EquivalenceTests`):

- **Loader validation** passes on both, and no node plane is a negative
  axial plane the engine's walk would misread.
- **Point contents** are equal at every point of a lattice every 8 units
  (offset by 4 so no sample lies on a brush plane) over the level and a
  12-unit margin; doorways are open exactly where the level joins them,
  and capped doors are solid.
- **Each kind's feature** reads as its material says in both maps: the
  pillar and step are solid leaves, the grate a grate leaf, the clip and
  the detail crate empty leaves; a segment through it is stopped by exactly
  the masks its contents are in.
- **Line traces** between every two room centres and 400 seeded pairs of
  open points stop at the same fraction in both maps under the solid,
  player and shot masks; in each map, walking the tree gives the same answer
  as clipping against every brush.
- **Reachability**: flooding the lattice's player-passable points, every
  room reaches exactly the rooms the joints connect it to; and a standing
  player's hull (32 x 32 x 72, as 5 x 5 x 10 lattice points) flooded from
  any room's centre reaches every placed room, in both maps.
- **Visibility**: the linked PVS equals the door-graph replay of the rooms'
  own vis and the joints, and covers everything the real vvis sees in the
  monolithic map.
- **Collision**: the world collision holds the same convexes in the same
  contents classes at the same places, and every room has some.
- **Faces**: every plane draws the same area in the same material, except at
  joined doorways (below).
- **Entities**: the same entities at the same places, facing the same way.

The flattened level is also checked, brush for brush and entity for entity,
against a monolithic map the generator builds on its own
(`Rooms3x3Arrangement.MonolithicVmf`), which shares no placement code with
the linker or the flattener.

### The known difference: doorway faces

`ssmap link` removes a joined socket's plug rather than compiling each room
twice. In each room's own compile the doorway's jambs, floor strip and
ceiling strip faced the solid plug, and vbsp emits no face between two
solids, so the linked map has no faces there: the doorway draws as a gap at
its edges unless something placed in the socket covers it. The faces fact
asserts that the linked map is short by exactly those surfaces (two jambs,
the floor strip and the ceiling strip through both walls of every joined
doorway) and by nothing else.

### The exhaustive sweep

`Rooms3x3EquivalenceTests.EveryArrangementInTheSweepMatchesItsMonolithicMap`
runs every criterion over more arrangements. It is skipped unless the
`SSMAP_ROOMS3X3_SWEEP` environment variable asks for it: `all` for every
valid arrangement (five to six hours of one core), or a count for that many
spread evenly through the enumeration:

```sh
SSMAP_ROOMS3X3_SWEEP=1000 dotnet test src/SourceSharp.Tests/SourceSharp.Tests.csproj -c Release \
    --filter "FullyQualifiedName~EveryArrangementInTheSweep"
```
