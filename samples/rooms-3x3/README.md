# 3x3 rooms sample

A level of nine rooms on a 3x3 grid, built twice: once by compiling five
room kinds with `ssmap room` and stitching them with `ssmap link`, and once
as one ordinary VMF of the same level compiled with `ssmap vbsp`. The test
suite rearranges the rooms into other valid levels and checks that the
linked map and the whole-map compile agree on everything a game can observe.

Everything in this folder except this README is generated by
`SourceSharp.MapGen.Rooms` and checked by a test to be exactly what the
generator writes. Do not edit the files by hand; change the generator and
regenerate.

## What is here

| Path | What |
| --- | --- |
| `gameinfo.txt` | A game that mounts only this folder, so the sample compiles with no Steam install. |
| `materials/rooms3x3/*.vmt` | The kit's materials. No textures ship; a missing base texture is only a warning. |
| `maps/<kind>.vmf` | The five rooms, each a sealed 256-unit box in its own cell. |
| `maps/<kind>.vmf.roomdef.json` | Each room's definition: name, grid, door kit and sockets. `ssmap room` reads it beside the VMF. |
| `layouts/rooms3x3.json` | The sample level for `ssmap link`. |
| `layouts/rooms3x3_turn{1,2,3}.json` | The same level turned a quarter, a half and three quarters: every room in another cell, turned. |
| `maps/rooms3x3*.vmf` | Each of those levels as one monolithic VMF: the reference the linked map is compared with. |

### The kit

Every room is a 256-unit cell with a 16-unit shell. A door socket is a
96-wide opening the full height of the interior, centred on a cell face,
filled by a plug brush of `rooms3x3/doorplug` (`%compileTrigger`, still
solid, so the room compiles sealed). `ssmap link` removes the plug at a
jointed socket and keeps it at a capped one.

| Kind | Sockets (room-local) | Feature |
| --- | --- | --- |
| `cross` | east, west, north, south | a structural pillar in the north-west corner |
| `tee` | east, west, north | a player-clip block (`rooms3x3/playerclip`) |
| `corner` | east, north | a grate post (`rooms3x3/grate`, `%compilePassBullets`) |
| `hall` | east, west | a `func_detail` crate |
| `end` | east | a step, and the level's one `info_player_start` |

Every room has a light at its centre. The features stand off the centre and
out of the doorways, so a room turned a quarter is a different map even when
its sockets look the same.

### The sample level

Rotations are quarter turns counter-clockwise seen from above; north is +y.

```
y=2   end    @3 (S)          hall  @1 (N capped, S)   corner @3 (S, E capped)
y=1   tee    @3 (S, N, E)    cross @0 (all four)      tee    @1 (N, S, W)
y=0   corner @1 (N, W capped) corner@0 (E, N)         corner @1 (N, W)
```

## Build and link it

From this folder, with `ssmap` built (`dotnet build src/SourceSharp.MapTools.slnx -c Release`
at the repository root puts it in `bin/Release/ssmap.dll`):

```sh
# compile each room into rooms/<kind>.room (the game is this folder: the map folder's parent)
ssmap room maps/cross.vmf  -out rooms
ssmap room maps/tee.vmf    -out rooms
ssmap room maps/corner.vmf -out rooms
ssmap room maps/hall.vmf   -out rooms
ssmap room maps/end.vmf    -out rooms

# link the level from the compiled rooms, without recompiling them
ssmap link layouts/rooms3x3.json -rooms rooms -out out/rooms3x3_linked.bsp

# the reference: the same level compiled whole
ssmap vbsp maps/rooms3x3.vmf

# both pass the loader's checks
ssmap check out/rooms3x3_linked.bsp maps/rooms3x3.bsp
```

Swap in `layouts/rooms3x3_turn1.json` and `maps/rooms3x3_turn1.vmf` (and so
on) for the turned levels; the rooms do not need recompiling. The outputs
(`rooms/`, `out/`, `maps/*.bsp`, `maps/*.prt`) are ignored by git.

## Regenerate it

```sh
dotnet run --project tools/RoomsSample -c Release -- --out samples/rooms-3x3    # rewrite the files
dotnet run --project tools/RoomsSample -c Release -- --check samples/rooms-3x3  # say what differs
dotnet run --project tools/RoomsSample -c Release -- --list                     # the arrangements the tests check
```

`Rooms3x3SampleTests.TheCheckedInSampleIsWhatTheGeneratorWrites` fails when
this folder and the generator disagree.

## What the tests check

### The arrangements

An arrangement puts the sample level's nine rooms (one cross, two tees, four
corners, one hall, one end) in any cells with any rotations. It is valid when
every shared wall has a socket on both sides or on neither, and the joints
connect all nine rooms. There are **85,088** valid arrangements
(`Rooms3x3Permutations.All`, a backtracking search in a fixed order).

The default test run checks **17** of them (`Rooms3x3Permutations.DefaultCases`):

1. the sample level and its three whole-level turns (4);
2. for each kind, the first valid arrangement with that kind in the centre
   cell, and the first with it in the corner cell (0, 0) (9: the cross's
   corner pick is the same arrangement as the corner's centre pick);
3. four arrangements drawn from the whole enumeration with a fixed seed.

### The criteria

The linked BSP and the monolithic BSP are not byte-equal and are not meant
to be: a whole-map compile builds one tree over all nine rooms, and the link
hangs nine room trees under a grid of cell planes. They are compared in what
a game observes (`Rooms3x3EquivalenceTests`):

- **Loader validation** passes on both, and no node plane is a negative
  axial plane the engine's walk would misread.
- **Point contents** are equal at every point of a lattice every 8 units
  (offset by 4 so no sample lies on a brush plane) over the level and a
  12-unit margin; doorways are open exactly where the layout joints them,
  and capped doors are solid.
- **Each kind's feature** reads as its material says in both maps: the
  pillar and step are solid leaves, the grate a grate leaf, the clip and
  the detail crate empty leaves; a segment through it is stopped by exactly
  the masks its contents are in.
- **Line traces** between every two room centres and 400 seeded pairs of
  open points stop at the same fraction in both maps under the solid,
  player and shot masks; in each map, walking the tree gives the same answer
  as clipping against every brush.
- **Reachability**: flooding the lattice's player-passable points, every
  room reaches exactly the rooms the layout's joints connect it to.
- **Visibility**: the linked PVS equals the door-graph replay of the rooms'
  own vis and the joints, and covers everything the real vvis sees in the
  monolithic map.
- **Collision**: the world collision holds the same convexes in the same
  contents classes at the same places, and every room has some.
- **Faces**: every plane draws the same area in the same material, except at
  jointed doorways (below).
- **Entities**: the same entities at the same places, facing the same way.

### The known difference: doorway faces

`ssmap link` removes a jointed socket's plug rather than compiling each room
twice. In each room's own compile the doorway's jambs, floor strip and
ceiling strip faced the solid plug, and vbsp emits no face between two
solids, so the linked map has no faces there: the doorway draws as a gap at
its edges unless something placed in the socket covers it. The faces fact
asserts that the linked map is short by exactly those surfaces (two jambs,
the floor strip and the ceiling strip through both walls of every jointed
doorway) and by nothing else.

### The exhaustive sweep

`Rooms3x3EquivalenceTests.EveryArrangementInTheSweepMatchesItsMonolithicMap`
runs every criterion over more arrangements. It is skipped unless the
`SSMAP_ROOMS3X3_SWEEP` environment variable asks for it: `all` for every
valid arrangement (five to six hours of one core), or a count for that many
spread evenly through the enumeration:

```sh
SSMAP_ROOMS3X3_SWEEP=1000 dotnet test src/SourceSharp.Tests/SourceSharp.Tests.csproj -c Release \
    --filter "FullyQualifiedName~EveryArrangementInTheSweep"
```
